# 分钱机制诊断

一个纯前端工具，零后端、零构建、零依赖（除 CDN）。

**L1（免费）** 做体检：从现象出发，判断你的分钱机制最可能是哪里出了问题。
**L2（¥199）** 给方案：接下来改什么、按什么顺序、什么条件算改对了。

边界写在产品里，也写在这里：

- 只做现金激励。股权、期权的具体条款涉及法律和财税，不碰。
- **不给比例数字。** 比例没有普适解，要由用户用自己的业务数据推出来。
- 输出是**待确认的假设**，不是结论。
- 一次只拧一个旋钮。同时动五个，三个月后分不清是哪个起了作用。

## 直接打开

双击 `index.html` 就能跑（全部是相对路径，不需要起服务）。
**本地版本永远比线上新** —— 想测就用本地，不用等部署。

```bash
python -m http.server 8899   # 想更接近线上
# 然后开 http://127.0.0.1:8899/
```

**实测模式**：地址后面加 `?observe=1`，右下角出现计时条（本轮 / 累计），
每过完一个团队自动归零，报告页会列出每个团队的用时。
不带这个参数，`observe.js` 整段代码不运行，对真实用户零影响。

## 改完要跑这四条

```bash
node tools/selfcheck.js           # 规则库有没有漏登记
node tools/check-manual-terms.js  # 手册里有没有用户看不懂的词
node tools/export-review.js       # 重导待填清单（改过 pay-data.js 就要跑）
```

**后两条不是可有可无的**：导出的 `.md` 里带一个源文件校验值，
不重跑的话，你手上那份跟代码就对不上了，而且**看不出来**。

## 规则库里有什么

| 东西 | 数量 | 说明 |
|---|---|---|
| 病因 `CAUSES` | 30 条 | 23 根因 + 7 衍生，分两层 |
| 症状 `SYMPTOMS` | 111 条 | 每条挂一个病因，带特异性（权重） |
| 旋钮 `KNOBS` | 5 个 | 考核口径 / 计提基数 / 保底与封顶 / 差距大小 / 机制用旧了 |
| 改法 `PLANS` | 18 个 | **L1 交给 L2 的键**，不是病因代码 |
| 两说卡 `TRADEOFFS` | 5 张 | 没有标准答案的地方，把两边代价摆出来 |
| 通用判断 `PRINCIPLES` | 6 条 | 命中才显示 |
| 验证时间窗 `CAUSE_FAMILY` | 6 档 | **病的钟**：这个病多久才被看见 |
| 改法的效果窗 `effectWindow` + `seeSpeed` | 18 个 | **药的钟**：改完多久能看出有没有用 |
| 约束属性 `CAUSE_CONSTRAINTS` | 30 × 3 | 这一步要花钱吗 / 动存量的人吗 / 是重设吗 |

**两个钟不要混**：病的钟说的是「病多久显形」，药的钟说的是「药多久见效」。
它们可能差得很远——R4 的病要两年才显形，但改对了下一个发钱周期就能看出来。

**约束属性挂在病因上、不挂在改法上**：18 个改法里有 5 个装着方向相反的病，
挂在改法上会给错警告（保底过高的人被提醒"要花钱"，而他改的其实是省钱的）。

## 两个自检各防什么

**`selfcheck.js` 专防「静默失败」** —— 这类错误不报错，只是答案慢慢变得不对：

- 孤儿病因（没有任何症状指向它 → 永远诊断不出来）
- 症状指向了不存在的病因
- 病因的 knob 值写错（「调整的思路」整块不渲染，页面上看不出来）
- 改法没登记、或指向不存在的改法
- 前置问的某个选项没登记影响（选了等于没选）
- 话术卡里出现「你/你们」（那是指控，不是证据句）
- 两说卡挂到不存在的病因上，或者缺了「中间路径」（缺了就变成单边建议）
- 改法缺 `effectWindow`／`seeSpeed` 写错（L2 的提醒会失效）
- **病因没登记约束属性**（L2 没法判断方案跟他处境打不打架）
- **注释里写的条数跟实际对不上**（数错东西也是错）

`selfcheck.js` 支持传一个路径，用来测它自己（拿一个故意改坏的文件喂给它）：

```bash
node tools/selfcheck.js path/to/file.js
```

浏览器里也有一份同样的检查（`validateRulebook()`），页面加载时跑，有问题在 console 报错。

**`check-manual-terms.js` 防的是「用户看不懂」** —— 扫两个规则文件里的**所有文案**
（注释不算，它到不了用户），查两类：

1. **禁用术语**（表在文件里）—— 判据是「直接念给老板听，他会不会先问这是什么意思」
2. **手册能不能独立成立** —— 用户每次只拿到一篇，所以内部编号、外部材料引用、
   跨篇引用都是死引用

## 写手册的评审标准

写在 `l2/js/l2-data.js` 的文件头。改手册之前先看那九条，核心是：

- 每篇必须能独立成立（用户手上只有这一篇）
- 成功判据是「行为变了」，不是「结果好了」
- 判据要**取在被激励的人身上**，不能取在公司拍板的产物上
  （「明年的计划」是上面定的，跟机制改没改没关系）
- 判据在旧机制下得是**做不出来**的
- 「坑」写**这次改动的副作用**，不是注意事项——「你做了 A，结果长出了 B」
- 「改错了」分四类：诊断错了 / 诊断不完整 / 执行没到位 / 起反作用

## 已知限制（记一笔，暂不修）

**症状 → 病因是一对一，但现实中是多对多。**

`SYMPTOMS[].cause` 只能填一个病因，自检也是按单数查的。可「部门之间为资源吵架」
既可以指向 R1（资源分配），也可以指向 D1（机制互相拆台）。

**这压着鉴别诊断的能力上限**：工具说得出「如果不是这个原因还可能是别的」，
但算不出「你勾的这几条同时也支持另一个病因」。

修法是「主指向 + 备选指向」——保留 `cause` 用于打分，另加一个可选的 `alt` 数组，
只在你确实觉得有歧义的地方加（估计 30-40 条，不是全部 111 条）。
不追求完整的多对多加权：那是 200 个权重决策，而这个规则库还要靠一个人维护。
